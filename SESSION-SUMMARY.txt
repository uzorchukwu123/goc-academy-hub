DONE THIS SESSION
------------------
Section 6 — Live classes (Zoom schedule) + student Timetable — COMPLETE.

Both sides of this were fake before this session: the admin console's
"Classes" panel had two hardcoded rows and a button that only toasted,
and the student Timetable showed one hardcoded Mon-Sun week — identical
for every student, with a comment already on it saying the real week
should come from the server. Both are now real:

  - server/server.js: new Appwrite-only `liveclasses` collection (no
    flat-file fallback, same as resources/videos) and five new routes —
    GET /api/classes (student, upcoming/non-cancelled), GET
    /api/admin/classes (console, full list), POST
    /api/admin/classes/upload (console, plain JSON — no file involved),
    PUT /api/admin/classes/:id (console, partial edit or status change),
    DELETE /api/admin/classes/:id (console, only a cancelled or
    completed class can be hard-deleted — the same "must not be live"
    guard resources/videos deletion already uses).
  - js/api.js: listClasses, listUpcomingClasses, createClass,
    updateClass, cancelClass, deleteClass added to the mock driver, the
    http driver, and the GOC.api facade — driver-parity tested (8/8).
  - js/app.js: the admin Classes panel now has a real scheduling form
    (subject, topic, tutor, date/time, duration, Zoom link) and a real
    list underneath (Mark completed / Cancel / Delete), built
    function-for-function against the existing admin video pattern. The
    student Timetable now loads real upcoming classes on login and
    rebuilds the week from them, falling back to the old demo week only
    when nothing real has been scheduled yet (so a brand-new deployment
    never shows a blank screen). A class block's Zoom link now opens in
    a new tab on tap, the same way a video's link already does.
  - sw.js: cache bumped goc-v27 -> goc-v28 (the client files touched by
    §6 changed, so returning users get the new shell).

One thing worth flagging: partway through, test-p10.js failed a rule
that says js/app.js must contain no `.sort(` call anywhere (ordering is
supposed to come from the server/shared engine, never be recomputed on
screen — the same rule that keeps league ranking from drifting
client-side). The first pass of this work had added two `.sort(` calls
in app.js. Fixed by relying on the server already returning classes
pre-sorted by scheduledAt — filtering or bucketing that array by weekday
preserves the order without needing to re-sort, so both calls were
simply removable. Re-ran the full suite after the fix: clean.

Verified: node -c clean on every changed file; full test suite run
(test/run.js) — all pure-JS suites pass, including test-p10.js (75/75,
the .sort( check now clean) and test-driver-parity.js (8/8). test-server.js
and test-security.js fail in this sandbox only because node_modules was
never installed here (no network access to run npm install) — same
pre-existing sandbox limitation as every previous round, not something
this session broke; re-run those two specifically once npm install is
available.

One manual deploy step this creates: the Appwrite `liveclasses`
collection needs to be created by hand with eight attributes (classId,
subject, topic, tutor, scheduledAt, durationMin, zoomLink, status) —
Appwrite doesn't auto-create collections or attributes. Until it exists,
every /api/classes and /api/admin/classes route either 503s (Appwrite
not configured at all) or fails per-request with a logged, caught error
(Appwrite configured but the collection missing) — it does not break any
other route.
