PHASE 5 — DONE THIS SESSION
--------------------------------------------------------------
Carried over from before this session, unchanged: render.yaml's
GOC_TRUST_PROXY and NODE_VERSION=20 fix, the Railway-schema research
(no inline env-var slot the way render.yaml has one), and the partial
default-secret-warning discovery in server.js's seed().

Done this session:
  - Closed the "refuses to boot (OR logs an impossible-to-miss warning)"
    item for real, in a way that resolves the ambiguity rather than
    picking one arbitrarily: the server now checks the ACTUAL STORED
    Founder/Academic Director passwords, console passcode, and signup
    code against the published demo defaults on EVERY boot — not just at
    first seed, using the same constant-time verifyPassword() real logins
    use, so an old data.json that was seeded long ago and never rotated
    is caught too, not just a fresh install. In a production-like run
    (NODE_ENV=production or GOC_NO_DEMO_SEED=1 — the same signal that
    already gates demo-account seeding) it refuses to start and exits
    with a boxed list of exactly which secrets are still default.
    Otherwise (local dev) it prints the same boxed warning to the console
    and keeps running. Also closed the "not yet confirmed" gap noted last
    session: GOC_PASSCODE now gets the same treatment as the two admin
    passwords and the signup code — all four are checked, not just the
    signup code.
  - Manually verified both branches in an isolated copy of the server
    (not the shipped data.json): confirmed exit code 1 with the warning
    banner when defaults are live in a simulated production boot, and
    confirmed a clean boot that stays up once real values are supplied
    via GOC_FOUNDER_PW/GOC_ACADDIR_PW/GOC_PASSCODE/GOC_SIGNUP_CODE.
  - Found and fixed a real bug while wiring the check in, the same way
    the Phase 4 migrate() bug was found — by reading the actual startup
    code path rather than assuming it was already handled: the
    Appwrite-success startup branch (hasAppwriteConfig() true, Appwrite
    init succeeds) never called seed() if data.json didn't exist yet,
    unlike the other two startup paths (bare local run, and the
    Appwrite-init-failed fallback). A fresh Appwrite deploy with no
    data.json on disk would have thrown ENOENT on the first read that
    needed staff/settings. Fixed with the same guard the other two paths
    already had.
  - Built the rotating local backup of server/data.json from scratch —
    nothing like this existed in the codebase before this session. Every
    boot takes one immediately (so a restart doesn't leave a long gap),
    then on an interval (GOC_BACKUP_INTERVAL_MIN, default 360 = 6h),
    writing timestamped copies into server/backups/ and pruning down to
    the most recent GOC_BACKUP_KEEP (default 28). A failed backup logs
    and continues rather than taking the server down. server/backups/ is
    covered by the same /server/ HTTP-serving denylist that already
    blocks server/data.json (confirmed via the existing test, not just
    assumed). This only covers the LOCAL-FILE data (staff, settings,
    questions, notes, attempts, and — on a non-Appwrite install —
    students). Made the explicit decision the prior session's notes
    flagged as open: on an Appwrite-Database install, student records
    never touch data.json, so this rotation does not reach them; that
    needs a separate Appwrite-side export/snapshot strategy using real
    Appwrite credentials this sandbox has never had access to — written
    up as an operator decision in DEPLOYMENT.md rather than guessed at
    or silently left uncovered.
  - Audited server-side logging for secrets or stack traces reaching the
    logs (distinct from the Phase 2 client-facing safeClientMessage fix,
    which only covers what the CLIENT sees). Read every console.error/
    console.warn/console.log call site and every throw new Error(...) in
    server.js. Found no case of a password, request body, or API key
    being interpolated into a log line or an error message — every
    error-path log uses err.message (which comes from static, non-secret
    strings this codebase itself throws) or, for uncaught
    exceptions/unhandled rejections only, the full err.stack, which is
    expected/standard practice for server-side debugging and never
    reaches the client. One line does print the literal default console
    passcode ('2027') to the log when GOC_PASSCODE isn't set — left as-is
    since it's the already-public demo default (documented in the
    readme), not a real secret, and the new boot-time check above means
    it can no longer stay '2027' in production anyway.
  - Wrote the full env-var checklist into DEPLOYMENT.md: the two new
    backup env vars, the default-secret boot behavior (what triggers
    refuse-vs-warn), Railway's NIXPACKS_NODE_VERSION=20 dashboard
    variable (railway.json's schema has no inline slot for this, unlike
    render.yaml's Blueprint spec — confirmed last session, documented
    this one), and confirmation that render.yaml already carries
    NODE_VERSION=20 and GOC_TRUST_PROXY so nothing further is needed
    there.
  - Documented that Render and Railway both terminate TLS at their own
    edge and proxy to this process over plain HTTP — this is also *why*
    GOC_TRUST_PROXY matters, so the two facts are now written next to
    each other in DEPLOYMENT.md instead of GOC_TRUST_PROXY's reasoning
    living on its own with no explanation of the underlying TLS setup.
  - Filled in DEPLOYMENT.md's old placeholder comment ("Manual
    accessibility and responsive QA checklist (Phase 3) will be appended
    here once that phase runs") with what Phase 3 actually found: the
    accessibility/contrast/reduced-motion work, the one real responsive
    bug found and fixed, the PWA install path built from scratch, and
    the "static analysis, not a real browser" caveat carried through
    explicitly rather than dropped.
  - Recreated .gitignore. Like PHASE6-NOTES.md's CI workflow file, this
    dotfile did not survive whatever export produced the zip this
    session started from (confirmed — no dotfiles or dot-folders of any
    kind were present at all, same as every other dotfile in this
    project's history). SECURITY-FIXES-2026-09-04.md documented that a
    .gitignore had existed and *why* (keep server/data.json and secrets
    out of any repo) but not its exact contents, so it was rebuilt from
    that stated intent: excludes server/data.json, the new
    server/backups/ directory, .env and .env.*, node_modules, and normal
