WCAG AA contrast pass — NOW DONE (finished this session, was "not
started at all"):

  - Method: extracted every same-rule background+color pair in
    css/styles.css (resolving CSS custom properties), computed WCAG
    contrast ratios, and checked each flagged pair against context
    (real body text needs 4.5:1; bold text under ~18.7px doesn't count
    as "large text" so still needs 4.5:1; SVG icons using
    stroke="currentColor" only need the 3:1 non-text-contrast bar, not
    4.5:1).
  - Real failures found and fixed (all fixes reuse a color already
    established elsewhere in the file for the identical background, so
    nothing here introduces a new palette value):
      - `.focus-tag` (signature focus-ring chip): red-on-#FDECEC was
        4.23:1. Changed to var(--red-deep), same swap already used by
        `.chip.red` and `.up-tag.admission` on the same background
        family. Now 5.66:1.
      - `.up-tag.news`: green-on-#E6F4EC was 4.42:1 (color was
        var(--green) instead of the darker literal already used for
        this exact chip elsewhere). Changed color to #106b34 — the same
        value `.chip.green` and `.wt-rev .verdict.ok` already use on
        this identical background. Now 5.83:1.
      - `.tabbar .tab.on` (desktop sidebar active-tab state, 14.5px
        bold — not large text by WCAG's definition): red-on-#FEECEC was
        4.24:1. Same red-deep swap as above. Now 5.68:1.
      - `--mute` token (#9AA3AF): the real systemic issue. It's used as
        actual secondary-text color in ~13 real spots (empty states,
        field hints, legal copy, unselected tab labels, "done" list
        items, etc.), all sitting at 2.2-2.6:1 against white/bg/card —
        nowhere close to AA. Every one of its usages is a `color:`
        declaration (verified none are used as a background or border),
        so fixing the single token fixes all ~13 spots at once with no
        other side effects. Darkened to #616D7E, same hue family,
        checked at 4.6-5.7:1 against all three backgrounds it actually
        appears on (white, --bg, --card).
  - Checked and confirmed NOT a real issue (left as-is, documented so
    it isn't re-flagged and re-investigated next session):
      - `.lp-crow .ci` (contact-icon circles): 4.24:1 looked like a
        failure at the token level, but it wraps an inline SVG with
        stroke="currentColor" — a graphical UI component, not text, so
        the applicable bar is 3:1 (non-text contrast), which it clears.
      - `.badge.lock .b`: color:var(--mute) on var(--card) was 2.23:1
        before the --mute fix, but the element only ever contains a lock
        emoji glyph (confirmed in index.html) — emoji ignore the CSS
        `color` property, so this declaration has no visible effect.
        Not touched; flagging so it isn't mistaken for a live bug later.
      - `body`'s own `color:var(--ink)` against its `#0e0f12` backdrop
        background: never actually rendered — `.phone` sits on top of
        it with its own opaque background, and body has no direct text
        children.
  - NOT exhaustively checked: this was a same-rule-pair scan plus a
    full check of every color token against the three main ambient
    backgrounds (white/--bg/--card). It does NOT verify every
    color-only declaration against whatever background actually ends up
    behind it in the live DOM (that needs a real browser/computed-style
    pass, which this environment doesn't have). `--gray` (#6B7280)
    borderline-fails against --card specifically (4.22:1) at the token
    level, but no rule in the file actually pairs `color:var(--gray)`
    with `background:var(--card)` in the same declaration, so this is
    left as a flag rather than a fix — worth a real-browser spot-check
    before calling contrast fully closed.
  - Full suite re-verified 15/15 green after all of the above.
