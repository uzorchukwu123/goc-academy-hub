7. Cohorts, Phase 1 (data model + API only) — DONE.

   Decision confirmed: Option B. A cohort can override the academy-wide
   dailyLimitMin, sessionMinutes, sessionWarnMinutes, objectiveMinutes and
   per-subject objectiveCounts. Each override field is nullable — null
   means "inherit the academy default" — so an unassigned student, or a
   cohort that overrides nothing, behaves exactly as before this feature
   existed. Cohort-scoped Results/Leaderboard and cohort-scoped enrolment
   are in scope for Phase 2, not built yet.

   server/server.js:
     - New Appwrite-only collection `cohorts` (APPWRITE_COHORTS_
       COLLECTION_ID = 'cohorts'), same no-flat-file-fallback convention
       as liveclasses/resources/videos.
     - cohortFromDoc(doc) maps a document onto {cohortId, name, status,
       dailyLimitMin, sessionMinutes, sessionWarnMinutes, objectiveMinutes,
       objectiveCounts, createdAt, updatedAt}.
     - effectiveSettingsFor(db, cohort) is the one place the merge
       happens: academy default, overridden field-by-field by whatever
       the student's cohort set. Every future caller (session limits,
       attempt limits, the objective sitting clock) should read through
       this function once it's wired in during Phase 2, rather than
       reading db.settings directly, so the merge logic never has to be
       duplicated at each call site.
     - GET /api/admin/cohorts, POST /api/admin/cohorts, PUT
       /api/admin/cohorts/:id (partial patch; sending an override field
       as null clears it back to "inherit"), DELETE /api/admin/cohorts/:id
       (blocked if any student is still assigned to it — same "empty it
       first" guard topics/resources deletion already uses).
     - PUT /api/students/:id/cohort — assign or clear (cohortId: null) a
       student's cohort. Dual-path (Appwrite students collection / local
       db.students), same shape as the existing .../active route.
     - `cohort` field added to the student record in both storage paths
       (appwriteStudentToRecord, migrate()'s per-student loop,
       publicStudent — surfaced to the student themself, not console-only
       like lastSeenAt).
     - GET /api/me/settings, need: 'student' — the cohort-resolved
       settings for whoever is signed in. Additive only: GET /api/settings
       is untouched and still returns the academy-wide default (it has no
       session, so it has no way to know whose cohort to apply, and stays
       what the pre-login signup screen reads).
     - Deploy note, same shape as §6's: the Appwrite `cohorts` collection
       needs its 8 attributes created by hand (cohortId, name, status,
       dailyLimitMin, sessionMinutes, sessionWarnMinutes, objectiveMinutes,
       objectiveCounts), and the `students` collection needs one new
       attribute added: `cohort` (string, nullable). Until both exist,
       cohort routes 503 or no-op the same way §6's did before
       `liveclasses` existed — nothing else breaks.

   js/api.js:
     - listCohorts, createCohort, updateCohort, deleteCohort,
       setStudentCohort, getMySettings added to the mock driver, the http
       driver, and the GOC.api facade — driver-parity tested (8/8).

   NOT done yet (Phase 2, next round):
     - The admin Cohorts panel in admOpen() (js/app.js) is still
       completely untouched — the original two hardcoded rows (S1/S2)
       and a "New cohort created" toast button. Needs a real form + list,
       built function-for-function against the Topics or Classes admin
       pattern (closest existing analogs), plus a cohort picker on the
       Students panel.
     - Nothing yet calls effectiveSettingsFor or GET /api/me/settings from
       the client. The session-length countdown, the daily study-window
       gate, and the objective-sitting clock all still read the
       academy-wide db.settings values everywhere they currently do —
       none of them are cohort-aware in the running app yet, only the API
       to resolve the numbers exists.
     - Results/Leaderboard have no cohort filter yet, on either the admin
       or student side.

6. Live classes (Zoom schedule) + the student Timetable — DONE.

   server/server.js:
     - New Appwrite-only collection `liveclasses` (APPWRITE_LIVECLASSES_
       COLLECTION_ID = 'liveclasses'). No flat-file fallback, same
       convention as resources/videos — every route 503s with "Appwrite
       Database is not initialized" if Appwrite isn't configured.
     - New classFromDoc(doc) helper maps a document onto
       {classId, subject, topic, tutor, scheduledAt, durationMin,
       zoomLink, status, createdAt, updatedAt} once, instead of repeating
       the mapping at every route the way the (older) video routes do.
     - GET /api/classes, need: 'student' — all documents, filtered in JS
       (not a Query filter, since a brand-new collection has no
       guaranteed indexes yet) to status !== 'cancelled' and scheduledAt
       in the future, sorted ascending by scheduledAt. Deliberately not
       filtered by subject server-side — same convention GET /api/videos
       already uses, where the subject narrowing happens client-side via
       studiesSubject().
     - GET /api/admin/classes, need: 'console' — every document, any
       status, same ascending sort.
     - POST /api/admin/classes/upload, need: 'console' — plain JSON body,
       not multipart (no file involved, despite the "/upload" path
       matching the plan's original wording). Validates subject, topic,
       scheduledAt (must parse as a date), zoomLink (must start
       http/https), durationMin (number, 1-600). classId is
       'CLS-' + a random hex string, same shape videoId already uses.
       status always starts 'scheduled'.
     - PUT /api/admin/classes/:id, need: 'console' — partial update; only
       fields actually present in the body are validated and written.
       status may be set to 'scheduled' | 'completed' | 'cancelled'.
     - DELETE /api/admin/classes/:id, need: 'console' — same "must not be
       live" family of guard resources/videos deletion already uses,
       adapted for a schedule instead of a publish flag: a class still
       'scheduled' is refused (400); only 'cancelled' or 'completed' can
       be hard-deleted. Already-gone (404 on lookup) returns
       { ok:true, alreadyGone:true } same as the other delete routes.

   js/api.js:
     - listClasses, listUpcomingClasses, createClass, updateClass,
       cancelClass, deleteClass added to the mock driver, the http
       driver, and the GOC.api facade — driver-parity tested (8/8).
     - Mock driver has no persistence for classes (same as
       listResources/listVideos in demo mode): listClasses/
       listUpcomingClasses return an empty array honestly; createClass/
       updateClass/cancelClass return demo:true acknowledgements;
       deleteClass refuses with "requires a server connection", matching
       deleteVideo/deleteResource's demo behaviour exactly.
     - cancelClass(id) is a client-side convenience — it calls the same
       PUT /admin/classes/:id endpoint updateClass uses, just with
       { status: 'cancelled' } already filled in. There is no separate
       cancel route on the server.

   js/app.js:
     - admOpen()'s `classes:` panel: the two hardcoded rows and the
       toast-only "Schedule class" button are replaced with a real form
       (subject via the shared subjSeg()/admSubj — the same shared
       subject-filter state every other admin content panel already
       uses — topic, tutor, a datetime-local picker, duration in
       minutes, Zoom link) and a real list underneath, fed by
       admLoadClasses()/admRenderClasses() — function-for-function
       against admLoadVideos()/admRenderVideos() (same "no host element,
       bail" guard, same per-subject filtered-empty-state breakdown
       showing which other subjects have classes). Actions per row:
       "Mark completed" and "Cancel" while a class is still scheduled;
       "Delete" once it's cancelled or completed (disabled by the server
       guard otherwise, so the button is only ever shown when it would
       succeed).
     - New admScheduleClass()/admCancelClass()/admCompleteClass()/
       admDeleteClass() functions, same busy-button / status-line /
       toast pattern admUploadVideo() already uses.
     - admOpen()'s post-render dispatch block: added
       `if(section === 'classes') admLoadClasses();`, next to the
       videos line.
     - The student Timetable: the hardcoded `var week = {...}` object is
       now the fallback only. New loadUpcomingClasses() calls
       GOC.api.listUpcomingClasses(); if the server returns any classes,
       it rebuilds `week` from them (bucketed by the weekday
       scheduledAt falls on, using SUBJECT_META[subject].color for the
       block colour — the same colours videoGradient() already draws
       from for consistency) and re-renders via buildWeek(). If the
       server returns nothing, `week` is left untouched, so a brand-new
       deployment with nothing scheduled still shows the demo week
       rather than a blank screen — same fallback rule
       loadPublishedResources()/loadPublishedVideos() already follow.
       loadUpcomingClasses() is added to the post-login hydration array
       alongside loadPublishedVideos(), wrapped in the same
       try/catch-per-function loop so a failure here can't strand a
       login.
     - dayBlocks() already filtered every block through studiesSubject()
       before this round — that's what keeps a class in a paper the
       student doesn't sit off their Timetable — so no change was needed
       there; a real class's `subj` field flows through the exact same
       filter a demo block's always has.
     - renderDay()'s per-block click handler now opens bl.zoomLink in a
       new tab when the block carries one (a real class), and falls back
       to the original toast(bl.subj+' · '+bl.topic) when it doesn't (a
       demo block) — same window.open(link, '_blank') decision video
       links already use, so there's no new "join" UI to design.
     - IMPORTANT CONSTRAINT HIT AND FIXED: test-p10.js asserts js/app.js
       contains no `.sort(` call anywhere ("the screen must never decide
       the order itself" — league ranking must come from the shared core
       engine, not be recomputed client-side). The first pass of this
       work added two `.sort(` calls in app.js (one in admRenderClasses,
       one sorting each day's blocks in loadUpcomingClasses) and failed
       that test. Fixed by relying on the server already returning
       classes pre-sorted by scheduledAt ascending on both routes —
       filtering that array by subject, or bucketing it by weekday,
       preserves the incoming order without needing to re-sort, so both
       `.sort(` calls were removable rather than replaced. Re-ran
       test-p10.js after the fix: 75/75 passing, this check included.

   DEPLOY NOTE: the new `liveclasses` Appwrite collection needs its
     attributes created by hand before this does anything in a live
     Appwrite deployment — nothing auto-creates them, same caveat
     VIDEO-LIVE-NOTES.md already gives for `videos` and this file already
     gave for `students.lastSeenAt`. Attributes needed: classId (string),
     subject (string), topic (string), tutor (string), scheduledAt
     (string, ISO datetime), durationMin (integer), zoomLink (string),
     status (string). Until the collection and its attributes exist,
     every /api/classes and /api/admin/classes route 503s with "Appwrite
     Database is not initialized" (if Appwrite isn't configured at all)
     or fails per-request with a logged, caught error (if Appwrite is
     configured but the collection is missing) — it does not break any
     other route, same isolation the lessonsPublished Appwrite calls in
     the Overview route already have.

4. Overview — live metrics — DONE.

   server/server.js:
     - publicStudent(db, s, opts) now takes an opts.console flag. When set,
       the returned object includes lastSeenAt; every other caller gets the
       same shape as before (unchanged for students viewing their own or
       nobody else's record). All 4 console call sites updated (GET
       /api/students, PUT /api/students/:id/active flat-file branch and
       Appwrite branch, POST /api/admin/students). The public sign-up route
       (POST /api/students, need: null) intentionally still calls
       publicStudent(db, rec) with no opts — a self-registering student
       should not receive a lastSeenAt field about themselves either, and
       this keeps that response shape exactly as it was.
     - New stampLastSeen(db, studentId) helper. Flat-file mode: finds the
       student, sets lastSeenAt = new Date().toISOString(), writeData(db)
       synchronously. Appwrite mode: calls updateAppwriteStudent(studentId,
       {lastSeenAt}) WITHOUT awaiting it (fire-and-forget, .catch just
       logs) — every logged-in screen polls session-info repeatedly, so
       awaiting a network write there would add latency to a request that
       has nothing to do with Appwrite otherwise.
     - Wired into the existing GET /api/auth/session-info route (Priority-9
       countdown poll) — calls stampLastSeen(db, d.id) only when
       d.role === 'student' (staff polling the same route are not
       students and should not get a "lastSeenAt" entry). That route now
       reads settings off one `const db = readData()` instead of a second
       inline readData().settings call, so the stamp and the settings read
       share one snapshot.
     - appwriteStudentToRecord(doc) now also maps lastSeenAt: doc.lastSeenAt
       || null.
     - New route: GET /api/admin/overview, need: 'console'. Returns
       { studentsTotal, activeToday, avgScorePercent, lessonsPublished }.
       studentsTotal/activeToday come from the student list (Appwrite or
       flat-file, whichever mode is active) — activeToday counts
       lastSeenAt within the last 24h at request time. avgScorePercent
       averages db.attempts where status === 'marked' AND typeof percent
       === 'number' (same guard clause used everywhere else in the app
       that averages a percent), null if no marked attempts exist yet.
       lessonsPublished counts published:true across both the `resources`
       and `videos` Appwrite collections in parallel (Promise.all) — 0 if
       Appwrite isn't configured, same as the admin resources/videos list
       routes already do, logged not thrown on failure so one bad query
       doesn't 500 the whole panel.
     DEPLOY NOTE: the Appwrite `students` collection needs a new
       `lastSeenAt` attribute added manually (string, holds an ISO
       datetime) — nothing auto-creates Appwrite attributes, same caveat
       VIDEO-LIVE-NOTES.md already gives for the `videos` collection's
       fields. Until that attribute exists, updateAppwriteStudent calls
       that try to set it will fail — caught and logged by
       stampLastSeen's .catch, so it fails silently rather than breaking
       login/session polling, but activeToday will read 0 until the
       attribute is added and students start polling again.

   js/api.js:
     - listOverview() added to the mock driver — derives studentsTotal
       from the in-memory students array and avgScorePercent from the
       in-memory attempts array using the identical guard clause; returns
       activeToday: 0 and lessonsPublished: 0 honestly (no lastSeenAt
       tracking in demo mode, and listResources/listVideos are already
       empty in demo mode for the same reason — not a bug to chase, matches
       the existing demo-mode convention).
     - listOverview() added to the http driver: GET /admin/overview.
     - listOverview() added to the GOC.api facade, forwarding to whichever
       driver is active.
     - test-driver-parity.js passes with it in place (verified below) —
       it's on both drivers with the same name, so the parity check that
       would have caught a one-sided method sees no mismatch.

   js/app.js:
     - admOpen()'s `overview:` panel markup: "Active today", "Average mock
       score" and "Lessons published" are no longer hand-typed
       (18 / 67% / 42). Each now has an id (admOvActive / admOvAvg /
       admOvLessons) and renders "…" until the real numbers land, same
       loading-placeholder convention admObjMin already used. "Students
       enrolled" and "Daily study window" were left exactly as they were —
       the plan only asked for the other three, and those two were already
       either correct (studentsData.length) or already live (state.limit).
     - New admOverviewLoad() function, following the same "fill itself in
       after the panel renders" pattern admLoadResources/admLoadVideos/
       admObjLoad already use: calls GOC.api.listOverview(), fills in the
       three ids on success, falls back to an em-dash on failure (network
       error, Appwrite not configured, etc.) rather than leaving "…"
       stuck forever.
     - admOpen()'s post-render dispatch block: added
       `if(section === 'overview') admOverviewLoad();`, placed first in
       that if-chain (overview is the console's landing panel — see
       `if(id === 'admin'){ admOpen('overview'); }` — so it's the first
       thing wired for symmetry with how it's the first panel opened,
       though order doesn't functionally matter since these are
       independent ifs, not else-ifs).
